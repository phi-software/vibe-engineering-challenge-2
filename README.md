## 1. 业务背景与目标

在具身智能数据采集和标注流程中，视频会被划分为多个动作片段（Segment）。每个片段包含开始时间、结束时间和动作名称。不合法的时间范围、超出视频边界的片段及时间重叠，都会影响数据的后续使用。

你需要开发一个轻量级 QC Workbench，完成以下闭环：

1. 用户在浏览器上传分段 CSV，并输入视频总时长（毫秒）。
2. 前端调用后端 API；后端解析 CSV、逐条执行 QC 规则。
3. 后端将本次 QC 报告与每条分段结果**写入 SQLite**，再返回报告。
4. 前端展示统计、错误原因和 **All / Valid / Invalid** 筛选。
5. 用户刷新页面后，前端通过报告 ID 请求后端，重新读取已存储的报告。

**本题不需要上传或播放真实视频。** 只检查分段元数据，不涉及视频编解码、AI 推理、真实对象存储、用户登录或机器人算法。必须接入真实后端与真实数据库；静态 Mock 数据或仅保存在浏览器中的结果不符合要求。

## 2. 必做功能

### 2.1 CSV 输入与视频时长

CSV 必须包含以下四列表头，列名区分大小写：

```csv
segment_id,start_ms,end_ms,action
s1,0,2000,Pick up cup
s2,2000,4200,Move cup
s3,4100,5000,Place cup
s4,5000,12000,Release cup
s5,6000,7000,
s6,7000,9000,Finish
```

本例的视频总时长为 `10000` 毫秒。

解析要求：

- 接受 UTF-8 CSV，支持 UTF-8 BOM、LF 和 CRLF 换行。
- 正确解析双引号字段、引号内逗号和转义双引号；**不得直接用逗号拆分行**。
- 四个必需列可采用不同的排列顺序，也允许额外列；仅处理必需列。
- `segment_id` 和 `action` 均作为原始字符串保留。`segment_id` 可以重复，不要求唯一；重复 ID 的记录也必须独立保留。
- `start_ms`、`end_ms` 应为十进制整数文本，可带首尾空白。空值、小数或非数字内容属于**片段级错误**，不应拒绝整个文件。
- 按 CSV 数据记录顺序处理；忽略文件末尾的空白行。结构性 CSV 错误（例如引号未闭合、列数与表头不一致）属于**文件级错误**。
- `durationMs` 通过 API 表单字段提交，必须是正整数（毫秒）。缺失、非整数、零或负数均为**请求级错误**。

为控制挑战范围，评测文件以小型 CSV 为主，通常不超过 100 条记录；不要求流式处理或大文件性能优化。

### 2.2 QC 规则

每条 Segment 均需执行以下规则，错误代码固定：

| 规则 | 判定条件 | 错误代码 |
| --- | --- | --- |
| 时间范围 | 时间无法解析为整数，或 `start_ms < 0`，或 `end_ms <= start_ms` | `INVALID_RANGE` |
| 视频边界 | 时间范围合法，但 `end_ms > durationMs` | `OUT_OF_BOUNDS` |
| 动作名称 | `action` 经 Trim 后为空 | `EMPTY_ACTION` |
| 片段重叠 | 与另一条符合重叠检查条件的 Segment 在时间上重叠 | `OVERLAP` |

时间区间统一采用**左闭右开**形式 `[start_ms, end_ms)`：

- `[0, 2000)` 与 `[2000, 4000)` 首尾相接，**不算重叠**。
- `[0, 2000)` 与 `[1900, 3000)` **算重叠**。
- 完全包含的时间区间也算重叠。

重叠检查约定：

1. 只有**时间范围合法且未超出视频边界**的 Segment 才参与重叠检查。带有 `INVALID_RANGE` 或 `OUT_OF_BOUNDS` 的记录不参与。
2. `EMPTY_ACTION` 不影响参与资格。一个时间合法、未越界但动作名为空的 Segment，仍可能同时拥有 `EMPTY_ACTION` 和 `OVERLAP`。
3. 发生重叠时，**涉及的双方都标记 `OVERLAP`**；即使一条记录与多条记录重叠，该错误代码也只出现一次。
4. CSV 的输入顺序不影响 QC 判断，但**返回结果必须保持输入顺序**。
5. 同一条 Segment 可以有多个错误。`errors` 去重并按 `INVALID_RANGE`、`OUT_OF_BOUNDS`、`EMPTY_ACTION`、`OVERLAP` 的顺序排列。其中 `INVALID_RANGE` 与 `OUT_OF_BOUNDS` 互斥。

`action` 的 Trim 指去除首尾常见空白字符；统一验收以 ASCII 空格、制表符等常规空白为主。非空的 `action` 应按原文返回，不要求转换大小写。

最终状态：

- `VALID`：无错误，`errors` 为 `[]`。
- `INVALID`：存在至少一个错误，`errors` 包含对应代码。

统计必须满足 `valid + invalid = total`，并且 `segments.length = total`。

### 2.3 SQLite 持久化

**SQLite 是必做项。** 每次文件级校验通过并执行 QC 后，系统必须把本次报告及所有 Segment 的检查结果写入**磁盘上的 SQLite 数据库文件**，不能仅存于进程内存或浏览器存储中。

数据库需要包含**至少两张关联表**，分别保存以下两类数据：

| 实体 | 至少保存的内容 |
| --- | --- |
| QC Report / Run | 报告唯一 ID、`durationMs`、`total`、`valid`、`invalid`、创建时间 |
| QC Segment | 所属报告 ID、记录顺序、原始 `segment_id`、解析后的起止时间、原始 `action`、状态、错误代码列表 |

例如使用 `qc_runs` 和 `qc_segments` 两张表，并通过报告 ID 关联。**表名、具体主键实现、ORM 和建表方式不限**；但每条 Segment 必须作为独立的数据库记录保存，不能只把整份报告保存为一个 JSON 字段，也不能用重复的业务 `segment_id` 覆盖其他记录。`errors` 可用 JSON 文本或其他可完整还原数组的方式存储。

持久化验收要求：

- 文件级或请求级错误**不创建报告**。
- 成功响应的报告必须已经持久化；不能先返回“保存成功”再异步写入。
- 通过报告 ID 查询时，数据必须从数据库正确恢复，包含全部 Segment、原始顺序及错误代码。
- **正常重启后端进程**（不删除数据库文件、不重建数据库），已保存的报告及 Segment 仍然存在，数据与重启前一致。
- 多次成功上传应产生不同的报告 ID，旧报告不能被新报告覆盖。
- 数据库写入失败时不能返回假成功；应返回合理的服务端错误。

不要求实现登录、数据库迁移系统、复杂事务恢复、分页、删除、编辑或分布式数据库。可以使用 SQLite 驱动、ORM 或原生 SQL；只需提供可复现的数据库初始化方式。

### 2.4 固定后端 API

为了统一自动化验收，必须实现以下**三个固定接口**。运行端口自选，并在项目 README 中说明。

#### `GET /api/health`

服务就绪时返回 HTTP `200`：

```json
{
  "status": "ok"
}
```

#### `POST /api/qc`

使用 `multipart/form-data` 上传，字段名固定：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `file` | File | 视频分段 CSV 文件 |
| `durationMs` | String | 正整数毫秒数，例如 `10000` |

输入有效时，后端执行 QC、保存数据库记录，并返回 **HTTP `200`** 与如下 JSON。允许添加其他字段，但以下字段的名称、类型和含义必须保持一致：

```json
{
  "runId": "qc-001",
  "createdAt": "2026-10-01T12:00:00Z",
  "durationMs": 10000,
  "total": 6,
  "valid": 2,
  "invalid": 4,
  "segments": [
    {
      "rowIndex": 1,
      "segmentId": "s1",
      "startMs": 0,
      "endMs": 2000,
      "action": "Pick up cup",
      "status": "VALID",
      "errors": []
    },
    {
      "rowIndex": 2,
      "segmentId": "s2",
      "startMs": 2000,
      "endMs": 4200,
      "action": "Move cup",
      "status": "INVALID",
      "errors": ["OVERLAP"]
    },
    {
      "rowIndex": 3,
      "segmentId": "s3",
      "startMs": 4100,
      "endMs": 5000,
      "action": "Place cup",
      "status": "INVALID",
      "errors": ["OVERLAP"]
    },
    {
      "rowIndex": 4,
      "segmentId": "s4",
      "startMs": 5000,
      "endMs": 12000,
      "action": "Release cup",
      "status": "INVALID",
      "errors": ["OUT_OF_BOUNDS"]
    },
    {
      "rowIndex": 5,
      "segmentId": "s5",
      "startMs": 6000,
      "endMs": 7000,
      "action": "",
      "status": "INVALID",
      "errors": ["EMPTY_ACTION"]
    },
    {
      "rowIndex": 6,
      "segmentId": "s6",
      "startMs": 7000,
      "endMs": 9000,
      "action": "Finish",
      "status": "VALID",
      "errors": []
    }
  ]
}
```

上例中的 `runId` 和 `createdAt` **仅为格式示例**，实际由系统生成。

响应字段约定：

- `runId` 为非空字符串，唯一标识本次报告；`createdAt` 为带时区信息的 ISO 8601 时间字符串。
- `durationMs`、`total`、`valid`、`invalid`、`rowIndex` 为 JSON 整数。`rowIndex` 从 `1` 开始，表示不含表头的数据记录顺序。
- `startMs`、`endMs` 是解析后的整数；原始字段无法解析时返回 `null`。能解析的负整数或越界整数保留原数值。
- `segmentId`、`action` 是原始 CSV 字符串；`segments` 顺序须与输入数据记录一致。
- `status` 仅允许 `VALID`、`INVALID`；`errors` 是按第 2.2 节顺序排列的错误代码数组。

#### `GET /api/qc/{runId}`

从**已持久化的 SQLite 数据**中读取指定报告。

- 找到报告：返回 HTTP `200`，JSON 结构和数据内容与该报告的 `POST /api/qc` 成功响应一致。
- 报告不存在：返回 HTTP `404`，JSON 包含 `code: "REPORT_NOT_FOUND"` 和非空 `error` 字符串。
- 重启后端后，使用同一 `runId` 仍能查询到历史结果。

不要求提供报告列表、删除或编辑 API。

#### 文件级与请求级错误

以下情况返回 HTTP `400`；JSON 必须包含固定 `code` 和非空 `error` 字符串：

| 场景 | `code` |
| --- | --- |
| 缺少 `file` 字段 | `FILE_REQUIRED` |
| 文件内容为空 | `EMPTY_FILE` |
| CSV 结构错误或无法正确解析 | `INVALID_CSV` |
| 缺少任一必要表头 | `MISSING_HEADER` |
| 只有表头、没有数据记录 | `NO_RECORDS` |
| `durationMs` 缺失、非整数或不大于零 | `INVALID_DURATION` |

```json
{
  "code": "INVALID_DURATION",
  "error": "durationMs 必须是正整数（毫秒）"
}
```

如果请求同时触发多个文件级错误，可以返回任一适用错误；验收时会分别构造单一错误条件。

**注意：** CSV 结构有效时，某个 Segment 的时间不合法、越界或动作为空，**整份请求仍返回 HTTP `200`**，并保存包含该条 `INVALID` 记录的完整报告。不要将片段级错误误判为文件级错误。

### 2.5 React 页面与历史报告

至少实现一个 React + TypeScript 页面：

1. 选择 CSV 文件，输入视频总时长，点击**开始检查**，调用真实的 `POST /api/qc`。
2. 处理期间显示 Loading，防止无意重复提交。
3. 展示 `total`、`valid`、`invalid`，以及按输入顺序排列的 Segment 列表，包括 ID、起止时间、动作、状态和错误说明。
4. 提供 **All / Valid / Invalid** 筛选。筛选只影响列表，不改变报告总统计，也不重新调用 QC 接口。
5. 文件无效、时长无效或 API 请求失败时，显示清楚的错误提示；新请求失败不能把上一次的结果冒充为新报告。
6. 成功创建报告后，显示或保留报告 ID。**页面刷新后**，能够基于该 ID 调用 `GET /api/qc/{runId}`，恢复并展示数据库中的完整报告。
7. 新的成功上传应显示新报告，不混入旧报告的 Segment；无可见结果时应显示空状态。

实现第 6 条时，可以将 `runId` 放在 URL 查询参数中，也可以放在浏览器本地存储中。**浏览器只保存用于重新查询的 ID，不能用本地保存的整份报告替代数据库读取。** 无需实现完整的历史报告列表或多页面路由。

允许任意 UI 组件库，不要求视频播放器、复杂动画或精细视觉设计。优先保证信息清楚、交互可用。

## 5. 技术与开发约束

- **前端必须使用 React + TypeScript**；后端语言和框架不限。
- **数据库必须使用本地持久化 SQLite**；不要求 PostgreSQL、Redis、Docker 或云数据库。
- **固定三条 API**：`GET /api/health`、`POST /api/qc`、`GET /api/qc/{runId}`。其他内部接口自由设计，不计入必做要求。
- 允许在单次 HTTP 请求内完成 QC 与数据库保存，不要求异步 Worker、任务队列或后台 Job。
- 不要求用户登录、租户隔离、视频上传、实际视频播放、视频解码或 AI 模型调用。

## 8. AI 使用规则与常见问题

**可以完全使用 AI 编程吗？** 可以。Cursor、Codex、Claude Code、OpenCode、GitHub Copilot 等均可，工具、模型和代码生成比例不限。你需要能够说明如何验证关键结果。

**为什么要使用数据库？** 本题需要考察一个小型全栈功能从请求、业务处理到数据库保存及历史读取的完整闭环。只保存到前端状态或后端内存不符合要求。

**必须使用某种后端语言、ORM 或框架吗？** 不需要。后端自由选择；数据库统一为本地 SQLite，以减少环境准备成本。可以使用原生 SQL。

**一定要建两张表吗？** 是。至少需要一张报告表和一张 Segment 表，建立关联关系。具体表名、字段命名和 ORM 不限制；每条 Segment 必须独立持久化。

**需要做历史报告列表或登录系统吗？** 不需要。保存一个 `runId`，能用固定读取接口重新加载该报告即可。

**重启后报告必须还在吗？** 是。正常停止并重启后端，保留相同 SQLite 文件，已保存的报告必须仍能读取。不要求处理断电时的复杂故障恢复。

**为什么一个 Segment 可能有多个错误？** 时间重叠与动作名称为空是独立检查项。时间合法且未越界的空动作 Segment 仍会参与重叠检查。

**首尾相接算重叠吗？** 不算。全部时间段均采用左闭右开区间 `[start_ms, end_ms)`。

**自动化测试必须提交吗？** 是。至少两项有业务断言、可实际运行的测试；更多边界测试属于加分项。

**是否需要实际视频、Docker、公网部署或付费 API？** 不需要。本题只使用 CSV 元数据和本地 SQLite。

**90 分钟没完成怎么办？** 可以提交现有代码，但请如实说明未完成部分和已知问题。开发时间建议与 7 天提交窗口是两个不同概念。

**可以使用脚手架或公开模板吗？** 可以。请遵守许可证，并在 README 中说明使用的公开业务模板来源。
